# Internationalization (i18n)

This document describes the current i18n model in Recordya Chat. The platform
supports English (`en`) and Polish (`pl`) across the core frontend, backend
user-facing messages, and Keycloak screens/emails.

## Runtime model

- The displayed language is static and config-driven.
- `DEFAULT_LOCALE` is the single source of truth.
- Supported values are `en` and `pl`; unset or unknown values normalize to `en`.
- There is no browser/`navigator` detection.
- There is no runtime language switcher or per-user language preference.
- Plugin-facing i18n is out of scope for now.

The locale flow is:

1. `DEFAULT_LOCALE` is read by backend `Settings`.
2. Backend normalizes it to `en` or `pl`.
3. Backend exposes it through `GET /auth/config`.
4. Frontend initializes i18next once during bootstrap, before React renders.
5. Keycloak receives the same value through `KEYCLOAK_DEFAULT_LOCALE` in Docker.

## Configuration

Set the root `.env` value:

```
DEFAULT_LOCALE=en        # en (default) | pl
```

Docker Compose passes it to:

- backend as `DEFAULT_LOCALE`,
- Keycloak as `KEYCLOAK_DEFAULT_LOCALE`.

If the value is missing, empty, or unsupported, backend normalizes it to `en`.

## Implementation rule

Do not hardcode user-facing text in core-owned frontend, backend, or Keycloak
surfaces. During implementation, every label, placeholder, title, button text,
status message, validation/error message, and email/login template string must
come from the appropriate locale catalog:

- frontend text must use `t("ns:key")`, `<Trans>`, or the shared `i18n.t(...)`
  instance outside React components,
- backend text must use `translate("domain.message", **params)`,
- Keycloak theme text must use `${msg("key")}` from the theme message bundles.

Only keep literal text inline when it is not user-facing, for example internal
log messages, test-only fixtures, stable machine values, or protocol constants.

## Frontend

Frontend i18n uses `i18next` plus `react-i18next`.

Files:

```
frontend/src/i18n/
├── index.ts
└── locales/
    ├── en/{common,auth,chat,settings,errors,reasoning}.json
    └── pl/{common,auth,chat,settings,errors,reasoning}.json
```

Namespaces: `common`, `auth`, `chat`, `settings`, `errors`, `reasoning`.

Use `useTranslation()` in React components:

```
const { t } = useTranslation();
t("settings:users");
```

Use `<Trans>` when a translated string contains React markup:

```
<Trans
  i18nKey="settings:deactivateConfirmBody"
  values={{ name, email }}
  components={{ bold: <span className="font-medium" /> }}
/>
```

Use the shared instance outside React components:

```
import i18n from "@/i18n";

i18n.t("errors:noResponseBody");
```

Pluralization and interpolation are handled by i18next. Polish plural keys use
the standard suffixes, for example `rows_one`, `rows_few`, `rows_many`, and
`rows_other`.

## Backend

Backend uses a lightweight dict-based catalog instead of gettext.

Files:

```
backend/src/core/i18n.py
backend/src/core/locales/en.py
backend/src/core/locales/pl.py
```

Use `translate()` for backend-owned user-facing messages:

```
from src.core.i18n import translate

translate("chat.error.rate_limit", limit=20)
```

Backend localization is currently used for API errors, SSE status messages,
friendly agent errors, and SQL plugin SDK validation messages. The SSE contract
does not change: events still carry a string `message`; the backend emits that
string already localized.

## Keycloak

Keycloak uses its native theme message mechanism.

Files:

```
keycloak/themes/recordya/login/messages/messages_en.properties
keycloak/themes/recordya/login/messages/messages_pl.properties
keycloak/themes/recordya/email/messages/messages_en.properties
keycloak/themes/recordya/email/messages/messages_pl.properties
```

Use `${msg("key")}` in `.ftl` templates. Polish characters in `.properties`
files should be escaped with `\uXXXX` sequences.

Both login and email themes declare `locales=en,pl`. The realm has
internationalization enabled, supports `en` and `pl`, and reads its default
locale from `KEYCLOAK_DEFAULT_LOCALE`.

### Existing realms

`keycloak/realm-export.json` is imported only when Keycloak starts with an empty
realm database. For existing environments, changing `KEYCLOAK_DEFAULT_LOCALE` or
the realm export does not automatically update the already-created realm.

After deploying an i18n/locale change to an environment with a persistent
Keycloak database, verify the live realm configuration with an authenticated
Keycloak Admin CLI session:

```
REALM="recordya"
kcadm.sh get "realms/${REALM}" --fields internationalizationEnabled,supportedLocales,defaultLocale
```

If the live realm does not match the desired locale model, update it explicitly:

```
REALM="recordya"
DEFAULT_LOCALE="pl"   # en | pl

kcadm.sh update "realms/${REALM}" \
  -s internationalizationEnabled=true \
  -s 'supportedLocales=["en","pl"]' \
  -s "defaultLocale=${DEFAULT_LOCALE}"
```

For example_customer deployments, use that deployment's realm name (for example
`<deployment-realm>`) and the same `DEFAULT_LOCALE` value passed to the backend
and Keycloak runtime configuration. Do not pass admin passwords in shell
history; authenticate `kcadm.sh` through the environment's approved
secret/session mechanism before running the verification or update.

## Adding or changing strings

### Frontend

1. Pick the existing namespace that matches the feature.
2. Add the same key to both `en/<ns>.json` and `pl/<ns>.json`.
3. In components, use `useTranslation()` and `t("ns:key")`.
4. For markup inside the sentence, use `<Trans>`.
5. Outside components, use `import i18n from "@/i18n"` and `i18n.t(...)`.

### Backend

1. Add the same key to `backend/src/core/locales/en.py` and `pl.py`.
2. Use `translate("domain.message", **params)`.
3. Keep interpolation in the catalog string, not in ad-hoc concatenation.

### Keycloak

1. Add the same key to English and Polish `.properties` files.
2. Reference it from `.ftl` with `${msg("key")}`.
3. Escape Polish characters in `messages_pl.properties`.

## Testing

- Frontend tests initialize i18next in `frontend/src/test/setup.ts` with `en`.
- Backend tests should instantiate `Settings(DEFAULT_LOCALE=...)` for locale
  behavior when needed.
- Keep Polish text in tests only when it is intentional test data, not UI copy.

## Out of scope

- Plugin-facing i18n for external plugin UI/nav labels.
- Runtime language switching.
- Per-user language preferences.
- Browser language detection.
